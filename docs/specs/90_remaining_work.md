### 3.1 `src/core/units.ts` — 物理定数と時間の書式

公開済みの記事では、`KB_EV` が 5 箇所(`cottrell-atmosphere`・`kirkendall-effect`・`gp-zones`・`ostwald-ripening` は 8.617e-5、`band-theory` は 8.617333e-5)、`formatDuration` が 4 箇所(区切りの違う実装が 3 通り)にある。

| 名前                            | 値 / 役割                                                 |
| ------------------------------- | --------------------------------------------------------- |
| `KB_EV`                         | 8.617333262 × 10⁻⁵ eV/K(CODATA 2018)                      |
| `KELVIN_OFFSET`                 | 273.15                                                    |
| `R_GAS`                         | 8.314462618 J/(mol·K)                                     |
| `EV_TO_KJ_PER_MOL`              | 96.48533212(1 粒子あたり 1 eV を kJ/mol に)               |
| `Q_E`                           | 1.602176634 × 10⁻¹⁹ C                                     |
| `EPS0_F_PER_CM`                 | 8.8541878128 × 10⁻¹⁴ F/cm                                 |
| `HBAR2_OVER_2ME`                | 0.0380998 eV·nm²(バンド理論の `HBAR2_OVER_2M` と同値)     |
| `HBAR_EV_FS`                    | 0.6582119569 eV·fs                                        |
| `YEAR_S` / `UNIVERSE_AGE_S`     | 1 年 = 365.25 日、宇宙の年齢 = 138 億年(≒ 4.35 × 10¹⁷ 秒) |
| `formatDuration(s, digits = 2)` | 秒を読者の単位の文字列にする(下記)                        |

`formatDuration` の表示: ナノ秒・マイクロ秒・ミリ秒・秒・分・時間・日・年・万年・億年のうち、**秒未満は値が 0.1 以上、秒以上は 1 以上になる単位**を選び、有効数字 `digits` 桁で書く。丸めた値が単位の上限に届いたら次の単位に繰り上げる(59.96 秒 →「1 分」)。宇宙の年齢以上は「宇宙の年齢の 2.5 倍」、1 万倍以上は「宇宙の年齢の 9.2 × 10⁸ 倍」。非有限・負の値は「—」。例: 1.4 × 10⁻⁴ →「0.14 ミリ秒」、720 →「12 分」、2.4 × 10¹¹ →「7600 年」、4 × 10²⁶ →「宇宙の年齢の 9.2 × 10⁸ 倍」(仕様書 14 図7 のフラッシュメモリの値)。

**公開済みの記事は移行していない**。`8.617e-5` → `8.617333e-5` は相対 4 × 10⁻⁵ の変更で、指数の中に入ると図の数値が表示桁で動き得る。`formatDuration` も区切りが記事ごとに違う(例: オストワルド成長は 90 秒を「90 秒」、新しい版は「1.5 分」)。移行する場合は記事ごとに別コミットにし、既存のテストがすべて通り、読み取りの表示値が変わらないことを確認する。**新しい 6 記事は必ずこちらを使う**。

| 名前                                   | 役割                                                                                   |
| -------------------------------------- | -------------------------------------------------------------------------------------- |
| `FONT_SANS` / `font(px, weight = 400)` | 図中の文字のフォント指定(`tokens.css` の `--font-sans` と同値)。`font(12)` →「12px …」 |

## 4. 既存記事の不整合の修正

### 4.1 古い相互参照(C-1)

並行開発で、各記事が「ほかの記事はまだない」前提で書かれたまま公開された。**今すぐ直せるもの**と、**相手の記事の公開時に直すもの**に分ける。

**再発の防止 — `<ArticleRef>`(P0 で導入済み)**: 本文で他の記事に言及するときは、`src/components/ArticleRef.astro` を使う。`topics.ts` の公開状態を見て、公開済みならリンク、準備中なら「(準備中)」を添えた文字を出す(前提バッジ・前後ナビと同じ方式)。相手の記事を公開した時点で本文の参照が自動でリンクになるので、並行開発でもこの種の不整合が起きない。

```text
…は、<ArticleRef slug="kirkendall-effect" />の記事で扱っています。
…は <ArticleRef slug="gp-zones">GPゾーン</ArticleRef
>の記事で扱います。
```

1 行目の形は記事タイトルをそのまま表示し、2 行目の形は表示する文字を指定する。前後の日本語との間に空白が入らないよう、**閉じタグの `>` の直後では改行しない**(改行するなら `</ArticleRef` の後で切り、次の行を `>の記事で` から始める — 既存ページの `</a\n>` と同じ書き方)。図注(`caption` 属性)は文字列なので使えない。図注では記事名を文字で書く。

## 6. 実装順と、並行実装の規則

```
P0(共通基盤 + 下準備 + C-1・C-2 の修正)── 単独でマージ … 済み(2026-10-23)
   │
   ├── 第 1 波(並行してよい): #12 フェルミ準位 / #3 構造因子 / #9 スピノーダル / #10 マルテンサイト / #14 トンネル効果と STM
   │
   └── 第 2 波: #13 pn 接合(#12 のマージ後 — #12 が作る共有モジュールを使う)

仕上げ(いつでも): P-1(発注者判断)・P-2 OGP・P-3 ダミー記事の削除・P-5 計測
```

**第 1 波を並行してよい理由**: P0 の下準備(§3.4)のあと、各記事のブランチが触る共有ファイルは次だけになる。

| 共有ファイル               | 各記事の変更                            | 衝突                                   |
| -------------------------- | --------------------------------------- | -------------------------------------- |
| `topics.ts`                | 自分の 1 行を `published: true` に      | 行が離れているので衝突しない           |
| `registry.ts`              | 自分のアンカーの直下に登録行を追加      | アンカーの間に空行があるので衝突しない |
| 他記事のページ(相互リンク) | §4.1 の「相手の公開時に直す」表のとおり | 直す行が記事ごとに違うので衝突しない   |
| `_shared/banddiagram.ts`   | **#12 だけ**が拡張する                  | 第 1 波で触るのは #12 だけ             |
| `src/core/fft.ts`          | **#9 だけ**が新設する                   | 新規ファイルなので衝突しない           |

それでも**マージは 1 本ずつ**行い、マージのたびに `main` を取り込んでから次をマージする(前回の経験から)。第 1 波の 5 本はどの順でマージしてもよい。

**本文で他の記事に言及するときは `<ArticleRef slug="…">` を使う**(§4.1)。第 1 波の 5 本は互いに準備中の記事へ言及し合うが、この部品で書いておけば、どの順で公開しても参照が自動でリンクになり、「公開済みなのに準備中と書いてある」不整合が再発しない。

**各記事のセッションへの依頼**: `docs/prompts/<番号>_<slug>_prompt.md` を読ませる(プロンプトの冒頭に「仕様書は作成済み — フェーズ 2 から」と追記してある)。**仕様書とプロンプトが食い違う場合は仕様書を優先**する(仕様書のほうが、実装済みの共有モジュールの実際の API と、本書の作成時に行った数値検証を反映している)。
